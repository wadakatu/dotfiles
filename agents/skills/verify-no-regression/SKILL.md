# /verify-no-regression

「このブランチ、PRの変更でデグレ、バグが起きないことを調査してください」を定型化したもの。
**証拠のない「問題ありません」を出さない**ことが目的。

## 処理フロー

1. **差分の全読**
    - 対象（引数の PR 番号 / ブランチ。未指定なら現ブランチ）の diff を base と比較して全て読む
    - 変更ごとに「影響しうる既存挙動」を列挙する。呼び出し元・公開契約（API レスポンス、型、イベント、enum 等）への波及を含める
    - diff が大きい場合はサブエージェントにファイル群を分担させてよいが、**結論に使う根拠は自分で検証する**

2. **テストゲート**
    - 対象リポジトリの規約に従い、影響範囲のテスト・lint・静的解析を実行する
    - 既存テストが変更・削除されている場合は「テストの弱体化（検知力の低下）でないか」を必ず確認する
    - テストが回帰を捕まえることを示すために実装を意図的に壊す（negative control）ときは、**赤くなったことだけを根拠にしない**。壊し方を間違えても赤くなるため。control を 1 本作るごとに次を確かめる
        - diff か grep で、意図した変更だけが入ったこと（`perl -pi` / `ruby -pi` の置換文字列では `$` が展開されるのでエスケープする）
        - シェルスクリプトなら `bash -n` で構文が通ること
        - FAIL したケース名が狙ったものと一致すること（exit code が非ゼロかどうかではなく、FAIL 一覧で照合する）
    - ガードを無効化する control は「決して成立しない条件」（例: `-lt 0`）にする。「常に偽」に反転すると、赤くなるのは happy path で、ガードを外したことにならない
    - control が緑のままなら、control を疑う前にテストの穴を疑う（「契約をコメントに書いた」だけでは何も固定していない）
    - 理由: 偽の control が 1 本でも混ざると、「テストは回帰を捕まえる」という主張の根拠が丸ごと崩れる

3. **実機確認**
    - リポジトリや環境に専用の検証 skill があれば、その手順と証拠の形に従う
    - フロントエンドの変更は実際に動かして確認する（対象ページを開き、変更点と周辺動線を操作。スクリーンショット等の証拠を残す）
    - API の変更は実リクエストまたは contract テストで確認する
    - 実機確認ができない場合は「できなかった」と明示する（省略を黙って通さない）

4. **証拠つき報告**
    - 報告に含めるもの: デグレ有無の結論 / 懸念点ごとの検証結果（何をどう確認したか）/ **検証できなかった領域とその理由・残リスク**
    - 未検証領域を「たぶん大丈夫」と書かない

## 注意事項

- 検証中に見つけた無関係の既存バグは、このフローの中で直さない（報告して別 issue を提案する）
