# research

「調査してください」「ベストプラクティスを確認して」「公式ドキュメントを見て」系の依頼に対する行動契約。
**出典のない主張をユーザーに返さない。**

## なぜこのスキルが必要か

ユーザーは裏取りのない回答を信用せず、出典の提示を求めることになる。最初から一次情報で裏取りした回答を返せば、この確認ループ自体が消える。

## トリガー

- 調査・ベストプラクティス・技術選定・「公式ドキュメントを確認して」系の依頼を受けたとき
- 自分がライブラリ / CLI / API の仕様を前提に実装・回答しようとしていて、その仕様を一次情報で確認していないとき

## 行動契約

1. **一次情報を必ず参照する**
    - 公式ドキュメント、公式リポジトリのソース・issue、言語 / フレームワークのリファレンスを WebFetch / WebSearch / context7 等で実際に読む
    - ローカルで挙動確認（実行・実験）できるものは実際に動かす
2. **主張ごとに出典を添える**
    - ドキュメントなら URL（可能ならセクション名）、コードなら `file:line`
    - 出典を確認できなかった主張は「未確認」と明示して区別する
3. **観測と仕様を区別する**
    - 「手元でこう動いた」（観測）と「仕様としてこう定められている」（spec）を混同しない。観測のみの場合はそう書く
4. **確信度と未検証点を明示する**
    - 結論の末尾に、確信が持てない点・調べきれなかった点を簡潔に添える
5. **鮮度を確認する**
    - バージョン依存の話題は対象バージョンを特定し、古い記事の情報をそのまま採用しない

## アンチパターン

- 学習時の記憶だけで「ベストプラクティスは〜です」と断定する
- ブログ記事の孫引きを公式見解のように書く
- 出典リストだけを長く貼る（テーマごとの要約 + 最小限のリンクにする）
- 自動生成された記述（OpenAPI の description、JSDoc 等）を実装の代わりに信じる（生成元のコードを読む）
