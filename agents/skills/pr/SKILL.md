# /pr

変更内容を適切な粒度でコミットし、プロジェクト指定の言語でPRを作成（概要・変更内容・関連情報のフォーマット付き）

## 処理フロー

1. **変更ファイルの解析**
    - `git status` で変更されたファイルを確認
    - ファイルの種類や変更内容を分析

2. **適切な粒度でのコミット作成**
    - `/commit` と同じ規約でコミットを作成する（既定=英語 Conventional Commits、プロジェクト側の明示規約が優先、`Co-Authored-By` トレーラー禁止）

3. **動かして確かめる**
    - 変更を動かして確かめる skill があれば（使える skill の一覧やリポジトリの CLAUDE.md で探す）、push の前に実行する。この変更ですでに確かめていれば省く
    - 確かめるケースと期待する結果は、diff・issue・依頼から自分で決める。正常系に加え、境界のケースと、バグ修正なら修正前の再現も入れる
    - 動かす対象が無い変更（ドキュメント・CI・設定だけ）や、環境の都合でできないときは、本文の「検証」にその旨を 1 行書く

4. **ブランチのプッシュ**
    - `git push -u origin <current-branch>` でリモートにプッシュ

5. **PR 作成**
    - `gh pr create` で作成
    - **リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` や直近 PR から読み取れるタイトル規約がある場合はそちらが最優先**で、下記の既定は使わない。テンプレートの条件付きセクション（migration チェックリスト等）は該当時に必ず埋める
    - タイトルは既定でプロジェクト指定の言語 + 種別プレフィックス: `Bugfix:` / `Refactoring:` / `New Feature:` / `Incident:` / `Document:`

6. **Orca への書き戻し**（Orca が管理する worktree のときだけ）
    - `orca worktree current --json` が `"ok": true` のときに、次の 2 つを実行する
        - `orca reference add <PR の URL> --worktree current --json`
        - `orca worktree set --worktree current --workspace-status in-review --comment "PR #<番号>" --json`
    - `"ok": false`（Orca 外）やコマンドの失敗は無視する。PR 作成は成功として扱う

## PR 本文の形

読み手は人間のレビュワーで、diff もコミットも別途読める。本文には判断に必要なことだけを書き、それ以外は diff とコミットに任せる。
この構成をこの順で埋め、ここに無い節は足さない。

```markdown
# 概要

<何をなぜ変えたか。要点だけ>

## 変更内容

- <レビュワーの判断に効く変更を 1 点 1 行。ファイル名の列挙ではなく「何が変わるか」>

検証: <何をどう確認したか 1 行。未実施ならその旨と、代わりに何を見たかを 1 行>

## 判断

- <聞かずに決めた実装の判断を 1 件 1 行。何を選んだか — 理由（出典の URL）。無ければこの節ごと省く>

## 関連情報

- <関連 issue / PR のリンク。無ければこの節ごと省く>
```

- 各行は結論の 1 行に畳む。コマンド出力・ログ抜粋・比較表・再現手順は本文ではなくレビューコメントに置き、本文からはそこを指す
- 未検証・スコープ外は削らず 1 行で明示する（省略ではなく圧縮する）
- `## 判断` に書くのは、ほかの選び方があり、レビュワーが別の案を選びうるものだけ（名前や書き方のように diff を見れば分かるものは書かない）。出典は公式ドキュメント・RFC・主要な実装の URL。リポジトリのテンプレートを使うときも、該当があればこの節を関連情報にあたる欄の前に足す
- 例外: 検証の skill が PR 本文に書く節（例: `## ローカル実機確認`）を決めているときは、その節を `## 関連情報` の前に置く
- **「別 issue で対応」「後続 PR で」に相当することを書くときは、書く前に `defer-to-issue` を発動して実際に issue を立て、本文にはその issue 番号を書く**

## 中断条件

以下は自分で解決せず、その場で止めてユーザーに確認する。

- **default ブランチにいる** — `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` と現在ブランチが一致したら中断。作業ブランチ名を提案して承認を取る
- **push するものが無い** — 未コミットの変更も base との差分もない場合は中断
- **同じブランチの PR が既に開いている** — `gh pr view --json url,state` で確認。あれば新規作成せず、既存 PR への push で足りるかを確認する
- **`gh` の認証エラー** — `gh auth status` の出力をそのまま提示して中断。自分で再認証を試みない
