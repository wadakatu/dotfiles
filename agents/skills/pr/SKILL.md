# /pr

変更内容を適切な粒度でコミットし、プロジェクト指定の言語でPRを作成（冒頭と判断だけを外に出し、詳細は折りたたむ形）

## 処理フロー

1. **変更ファイルの解析**
    - `git status` で変更されたファイルを確認
    - ファイルの種類や変更内容を分析

2. **適切な粒度でのコミット作成**
    - `/commit` と同じ規約でコミットを作成する（既定=英語 Conventional Commits、プロジェクト側の明示規約が優先、`Co-Authored-By` トレーラー禁止）

3. **動かして確かめる**
    - 変更を動かして確かめる skill があれば（使える skill の一覧やリポジトリの CLAUDE.md で探す）、push の前に実行する。この変更ですでに確かめていれば省く
    - 確かめるケースと期待する結果は、diff・issue・依頼から自分で決める。正常系に加え、境界のケースと、バグ修正なら修正前の再現も入れる
    - 動かす対象が無い変更（ドキュメント・CI・設定だけ）は、詳細の「検証」にその旨を書く。環境の都合で確かめられなかったときは、外の「未検証」に 1 行書く

4. **ブランチのプッシュ**
    - `git push -u origin <current-branch>` でリモートにプッシュ

5. **PR 作成**
    - `gh pr create` で作成
    - **リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` や直近 PR から読み取れるタイトル規約がある場合はそちらが最優先**で、下記の既定は使わない。テンプレートの条件付きセクション（migration チェックリスト等）は該当時に必ず埋める
    - タイトルは既定でプロジェクト指定の言語 + 種別プレフィックス: `Bugfix:` / `Refactoring:` / `New Feature:` / `Incident:` / `Document:`
    - draft で出したときは、ユーザーへの報告に draft にした理由と、ready にする条件を書く

6. **Orca への書き戻し**（Orca が管理する worktree のときだけ）
    - `orca worktree current --json` が `"ok": true` のときに、次の 2 つを実行する
        - `orca reference add <PR の URL> --worktree current --json`
        - `orca worktree set --worktree current --workspace-status in-review --comment "PR #<番号>" --json`
    - `"ok": false`（Orca 外）やコマンドの失敗は無視する。PR 作成は成功として扱う

## PR 本文の形

読み手は人間のレビュワーで、まず読むのは折りたたみの外だけ。外には「読む価値があるか」と「どこに判断が要るか」が分かる分だけを置き、残りは `<details>` に畳む。
この構成をこの順で埋め、下の決まりが挙げる節のほかは足さない。

```markdown
<冒頭 1〜2 文。何が困っていたか → この PR でどうなるか>

## 判断

- <聞かずに決めた実装の判断（スコープ外にしたことを含む）を 1 件 1 行。何を選んだか — 理由。3 件まで。無ければこの節ごと省く>

未検証: <確かめていないことを 1 行。無ければこの行ごと省く>

Closes #<この PR で閉じる issue>

<details>
<summary>詳細</summary>

### 変更内容

- <レビュワーの判断に効く変更。ファイル名の列挙ではなく「何が変わるか」>

### 検証

<何をどう確かめたか。コマンド出力・比較表・再現手順もここ>

</details>
```

- 折りたたみの外に置くのは、冒頭（画面が変わる変更は、その直後にスクリーンショット 1 枚）・判断・未検証・関連 issue / PR の行だけ。冒頭に見出しは付けない
- `<details>` は行頭に属性なしで書き、`</summary>` の後と `</details>` の前後に空行を置く（空行が無いと、中や直後の見出しが Markdown として描画されない）
- 関連の行は、この PR のマージで閉じてよい issue だけ `Closes #N`、参照するだけの issue / PR は `Refs #N` と書く。閉じる issue が複数なら `Closes #1, closes #2` のように 1 件ずつキーワードを付ける（[GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)）。無ければ行ごと省く
- 冒頭は 2 文まで、合わせて 150 字以内。「何が困っていたか → どうなるか」を書き、経緯・実装方法・ファイル名・件数の内訳は書かない
- `## 判断` に書くのは、ほかの選び方があり、レビュワーが別の案を選びうるものだけ（名前や書き方のように diff を見れば分かるものは書かない）。意図して扱わなかったこと（スコープ外）もここに書く。1 件は出典の URL を除いて 80 字以内で、理由は 1 つ。条件や例外の列挙は詳細の「変更内容」に書く
- 判断が 4 件以上あるときは、既存の挙動が変わるものと、誤ったときの影響が大きいものを外に 3 件残し、残りは詳細に `### 判断（続き）` として書く
- 出典（公式ドキュメント・RFC・主要な実装の URL）は、理由が外部の仕様や実装に依るときだけ、行末に `（[名前](URL)）` で付ける。依らない判断に飾りの出典を付けない
- 確かめていないことは詳細に埋めず、外の「未検証」の 1 行（80 字以内）に並べて明示する。確かめる代わりに見たものがあれば添える。収まらない内訳は詳細の「検証」に書く。動かす対象が無い変更（ドキュメント・CI・設定だけ）は未検証に当たらず、詳細の「検証」にその旨を書く
- 詳細の「変更内容」は 1 点 1 行。diff を見れば分かること（ファイル名、追従しただけのテストや README）と、作業の経緯（試して捨てた案、レビューの往復、直した指摘）は詳細にも書かない
- 既存の挙動を変えない意図の変更（リファクタ・移行・置き換え）では、詳細の「検証」とユーザーへの報告の両方に、何と何を比べて何が一致したかを書く（例: 変更前後で同じ入力の応答・画面・テスト結果が一致した）。比べていなければ、外の「未検証」に、比べていないことと理由を書く
- リポジトリのテンプレートを使うときは欄の構成に従う。チェックリストと条件付きの欄は畳まずにそのまま埋める。文章の欄は結論の 1〜2 文にし、長い中身（表・出力・変更点の一覧）だけを欄の中で `<details>` に畳む。`## 判断` と「未検証」の行は、該当があれば関連情報にあたる欄の前に足す
- 例外: 検証の skill が PR 本文に書く節（例: `## ローカル実機確認`）を決めているときは、その節を `</details>` の後（本文の最後）に、空行を挟んで置く。この節は畳まず、下の字数にも入れない
- 作成の前に本文をファイルに書き、折りたたみの外の字数を URL を除いて数える: `awk '/^<details>/{exit} NF' <本文ファイル> | sed -E 's/\(https?:[^)]*\)//g' | wc -m`。リポジトリのテンプレートを使わない PR で 600 字を超えたら、外に出しすぎなので詳細へ移す
- **「別 issue で対応」「後続 PR で」に相当することを書くときは、書く前に `defer-to-issue` を発動して実際に issue を立て、本文にはその issue 番号を書く**

## 中断条件

以下は自分で解決せず、その場で止めてユーザーに確認する。

- **default ブランチにいる** — `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` と現在ブランチが一致したら中断。作業ブランチ名を提案して承認を取る
- **push するものが無い** — 未コミットの変更も base との差分もない場合は中断
- **同じブランチの PR が既に開いている** — `gh pr view --json url,state` で確認。あれば新規作成せず、既存 PR への push で足りるかを確認する
- **`gh` の認証エラー** — `gh auth status` の出力をそのまま提示して中断。自分で再認証を試みない
