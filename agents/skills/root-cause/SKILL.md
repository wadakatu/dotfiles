# /root-cause

**原因を調べ終えるまで修正を書かない。** 症状への当て布は、別の場所で同じバグを生む。

superpowers の systematic-debugging（MIT, Jesse Vincent）と、mattpocock/skills の diagnosing-bugs（MIT, Matt Pocock, 5863806）の要点を抜き出したもの。

## 処理フロー

1. **赤くなる確認を 1 コマンドにする**
    - このバグで赤くなり、直れば緑になるコマンドを 1 つ作り、実行して赤を見る。判定するのは報告された症状そのもの（「エラーなく動く」ではない）。数秒で終わり、毎回同じ結果になる形に絞る。これが無いまま 4（仮説）へ進まない
    - 手段は上から、届く最初のもの: 失敗するテスト → curl → CLI と固定入力（正しい出力と diff）→ ヘッドレスブラウザ → 記録したリクエストの再生 → 最小の harness
    - 時々しか出ないなら、繰り返し回して再現率を上げる。作れなければ、試した手段を挙げて止まり、再現できる環境か記録（ログ・HAR）を頼む

2. **調べる**
    - エラーとスタックトレースを最後まで読む。行番号・エラーコード・警告も見る
    - 直近の変更（`git log` / `git diff`、依存や設定の更新、環境差）を見る
    - 層をまたぐ不具合（CI → build → 署名、API → service → DB など）は、境界ごとに入出力をログに出して 1 回走らせ、どの層で壊れるかを特定してから中を調べる
    - エラーが深い所で出るなら、その悪い値がどこから来たかを呼び出し元へ遡る。直すのは値が生まれた所で、エラーが出た所ではない

3. **見比べる**
    - 同じコードベースの中で、似ていて動いているものを探す
    - 壊れている側との差を、小さなものも含めて全部書き出す。「これは関係ないはず」で外さない

4. **仮説を 1 つ立てて確かめる**
    - 「X が原因だと考える。理由は Y」と書く
    - 確かめる変更は最小にし、変数は 1 つずつ動かす
    - 外れたら、変更を足し重ねずに新しい仮説を立てる。分からないことは分からないと言う

5. **直す**
    - 1 のコマンドを回帰テストとして残す（テストにできる場所が無ければ、そう報告する）
    - 根本原因に 1 か所だけ手を入れる。ついでのリファクタリングや改善は混ぜない
    - 1 のコマンドが緑になり、他のテストが壊れていないことを確かめる

## 止まる条件

- **修正が 3 回外れた** — 4 回目を試さない。直すたびに別の場所で壊れるなら、作りそのものが問題のことが多い。分かったことをまとめてユーザーと相談する
- 次の考えが浮かんだら 2 に戻る（1 のコマンドがまだ無ければ 1 から）: 「とりあえず直して後で調べる」「X を変えて動くか見る」「いくつかまとめて変えてテストする」「たぶん X だから直す」
- 調べ尽くしても原因が環境・タイミング・外部要因だった場合は、調べたことを記録し、適切なエラー処理とログを入れて報告する。原因が分からないまま「直った」と言わない
