# /root-cause

**原因を調べ終えるまで修正を書かない。** 症状への当て布は、別の場所で同じバグを生む。

superpowers の systematic-debugging（MIT, Jesse Vincent）の要点を抜き出したもの。

## 処理フロー

1. **調べる**
    - エラーとスタックトレースを最後まで読む。行番号・エラーコード・警告も見る
    - 毎回再現できるか確かめる。できなければ推測で直さず、再現条件を集める
    - 直近の変更（`git log` / `git diff`、依存や設定の更新、環境差）を見る
    - 層をまたぐ不具合（CI → build → 署名、API → service → DB など）は、境界ごとに入出力をログに出して 1 回走らせ、どの層で壊れるかを特定してから中を調べる
    - エラーが深い所で出るなら、その悪い値がどこから来たかを呼び出し元へ遡る。直すのは値が生まれた所で、エラーが出た所ではない

2. **見比べる**
    - 同じコードベースの中で、似ていて動いているものを探す
    - 壊れている側との差を、小さなものも含めて全部書き出す。「これは関係ないはず」で外さない

3. **仮説を 1 つ立てて確かめる**
    - 「X が原因だと考える。理由は Y」と書く
    - 確かめる変更は最小にし、変数は 1 つずつ動かす
    - 外れたら、変更を足し重ねずに新しい仮説を立てる。分からないことは分からないと言う

4. **直す**
    - 先に、失敗を再現するテスト（無理なら使い捨てのスクリプト）を作る
    - 根本原因に 1 か所だけ手を入れる。ついでのリファクタリングや改善は混ぜない
    - 再現テストが通り、他のテストが壊れていないことを確かめる

## 止まる条件

- **修正が 3 回外れた** — 4 回目を試さない。直すたびに別の場所で壊れるなら、作りそのものが問題のことが多い。分かったことをまとめてユーザーと相談する
- 次の考えが浮かんだら 1 に戻る: 「とりあえず直して後で調べる」「X を変えて動くか見る」「いくつかまとめて変えてテストする」「たぶん X だから直す」
- 調べ尽くしても原因が環境・タイミング・外部要因だった場合は、調べたことを記録し、適切なエラー処理とログを入れて報告する。原因が分からないまま「直った」と言わない
