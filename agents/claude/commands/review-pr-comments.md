# /review-pr-comments

PRのレビューコメントを取得し、現在のコードと照合して各コメントの妥当性を判定する。
修正が必要なものは自動で修正し、確認済みのコメントにリアクションを付与する。

## 処理フロー

### 1. PRコメントの取得

```bash
# PR番号を特定（現在のブランチから）
gh pr view --json number -q '.number'

# レビューコメントを取得（--paginate 必須: 無いと 30 件で切れて 31 件目以降が黙って漏れる）
gh api --paginate repos/{owner}/{repo}/pulls/{number}/comments --jq '.[] | "ID: \(.id)\nFile: \(.path)\nLine: \(.line)\nBody: \(.body)\n---"'
```

### 2. 現在のコードとの照合

各コメントについて以下を確認する:

1. **コメントが指摘するコード箇所を特定** - ファイルパスと行番号から該当コードを読む
2. **現在のコードと比較** - コメントが書かれた時点のコードと現在のコードを比較し、既に修正されているか判定
3. **指摘の妥当性を検証** - 指摘が技術的に正しいか、現在のコードに該当する問題があるかを確認

### 3. コメントの分類

各コメントを以下の3つに分類する:

#### 修正済み
- 後続のコミットで既に対応されている指摘
- コードを確認し、指摘された問題が解消されていることを確認

#### 要修正
以下のすべてを満たす場合:
- 指摘が技術的に正しい
- 現在のコードにまだ問題が残っている
- 修正による副作用リスクが低い

#### 対応不要
以下のいずれかに該当する場合:
- 指摘が技術的に誤っている（例: 実際には問題にならないケース）
- 現在の実装で問題ない合理的な理由がある
- 将来的な改善提案であり、このPRのスコープ外
- テスト追加など別PRで対応すべき内容

### 4. 修正の実施

「要修正」に分類されたコメントについて:

1. 該当ファイルを修正
2. CLAUDE.mdのコーディング規約に準拠していることを確認
3. プロジェクト規定のリンター/フォーマッタを実行して検証（規定は対象リポジトリの CLAUDE.md / Makefile / package.json scripts から特定する。ツール名をこのコマンドにハードコードしない）
4. 修正内容をコミットしてプッシュ

### 5. リアクションの付与

分類に応じてGitHub APIでリアクションを付与する:

```bash
# 修正済み / 要修正（対応した） → 👍
gh api repos/{owner}/{repo}/pulls/comments/{id}/reactions -f content="+1" --method POST

# 対応不要 → 👎
gh api repos/{owner}/{repo}/pulls/comments/{id}/reactions -f content="-1" --method POST
```

### 6. 対応不要コメントへの返信

「対応不要」に分類したコメントには **必ず理由を reply で残す**。👎 リアクションだけだと、レビュワーが後から見たときに「なぜ対応されなかったか」が辿れないため。

```bash
# コメントに reply を投稿
gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies \
  -f body="..." --method POST
```

返信に含めるべき情報:

1. **判断理由** - 技術的に誤っている / 既存規約に沿った省略 / 既に別コミットで対応済み など
2. **根拠** - sibling ファイル / CLAUDE.md ルール / 該当コミットハッシュ などの具体的なポインタ
3. **スコープの扱い** - 「本 PR のスコープ外」「別 issue 化推奨」など、フォローアップの方向性

例:

> sibling の `V2/Admin/OAuth/*Controller.php` も同じ invokable パターンで `__invoke` に PHPDoc を付けていないため、リポジトリ内の既存規約に合わせて省略します。PHPDoc を必要とするなら sibling 全体で統一したほうが一貫性があり、本 PR のスコープ外と判断しました。

> CodeRabbit の前提が古いコミットです。現在の `UserOAuthDisabledException::render()` は `expectsJson()` で分岐しブラウザに `USER_APP_URL?error=oauth_disabled` でリダイレクトする（コミット e842b1cea）ので、OAS の description と Location ヘッダー記述は実装と一致しています。

### 7. 結果レポート

最後に分類結果のサマリーを表示する:

```markdown
### 修正済み（👍）- N件
| コメント | 内容 | 対応状況 |
|---------|------|---------|
| #ID | 指摘の要約 | どのコミットで修正済みか |

### 要修正 → 修正完了（👍）- N件
| コメント | 内容 | 修正内容 |
|---------|------|---------|
| #ID | 指摘の要約 | 何をどう修正したか |

### 対応不要（👎）- N件
| コメント | 内容 | 理由 |
|---------|------|------|
| #ID | 指摘の要約 | 対応不要と判断した理由 |
```

## 判定のガイドライン

### 妥当な指摘の例
- バグや潜在的なランタイムエラーの指摘
- プロジェクトのコーディング規約（CLAUDE.md）違反
- セキュリティ上の懸念
- エラーハンドリングの不備
- データ整合性のリスク

### 対応不要になりやすい指摘の例
- 「テストを追加してください」（別PRのスコープ）
- 現在の仕様上問題にならないエッジケースの指摘
- 過度なリファクタリング提案
- パフォーマンス最適化（ボトルネックでない箇所）
- キー順序の違いによる誤検知など、実際には発生しない問題の指摘

## 注意事項

- コメントを確認する前に、必ず最新のコードを読んでから判定する
- 自動レビューツール（CodeRabbit等）と人間のレビュー、両方のコメントを対象にする
- 修正時はCLAUDE.mdの規約に従い、プロジェクト規定のリンターを通す（例: studio-auth なら `make lint`）
- 判断に迷う場合は「対応不要」ではなく、ユーザーに確認を取る
- **対応不要 (👎) は reply で理由説明を必ず残す** — 👎 だけだと後からレビュワーが辿れない
