# /pr

変更内容を適切な粒度でコミットし、プロジェクト指定の言語でPRを作成（概要・変更内容・関連情報のフォーマット付き）

## 処理フロー

1. **変更ファイルの解析**
    - `git status` で変更されたファイルを確認
    - ファイルの種類や変更内容を分析

2. **適切な粒度でのコミット作成**
    - `/commit` と同じ規約でコミットを作成する（既定=英語 Conventional Commits、プロジェクト側の明示規約が優先、`Co-Authored-By` トレーラー禁止）

3. **ブランチのプッシュ**
    - `git push -u origin <current-branch>` でリモートにプッシュ

4. **PR作成（プロジェクト指定の言語、指定フォーマット）**
    - GitHub CLI (`gh pr create`) を使用してPR作成
    - **リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` や明示的な PR タイトル規約（直近の PR タイトルから判断）がある場合はそちらを最優先**し、以下の既定フォーマットは使わない。テンプレートの条件付きセクション（migration チェックリスト等）は該当時に必ず埋める
    - PRタイトルは変更内容に応じて以下のルールに従ってプロジェクト指定の言語で生成：
        - Bugfix: `Bugfix: 〜`
        - Refactoring: `Refactoring: 〜`
        - New Feature: `New Feature: 〜`
        - Incident: `Incident: 〜`
        - Document: `Document: 〜`
    - PR詳細は以下のフォーマットを使用：

```markdown
# 概要

[PRの簡単な概要を1,2行で記述]

## 変更内容

[変更点を簡潔に説明してください]

- [自動生成された変更内容の説明]

## 関連情報

[Issue番号またはリンクを記載してください]

- [関連するIssue情報（あれば）]
```

5. **検証の記述は畳む**
    - **コマンド出力・比較表・ログ抜粋を PR 本文に貼らない。** 「何をどう確認したか」を 1 項目 1 行に要約する
      （例: `exit code 伝播: 旧形式は成功、新形式は exit 2 で失敗（実 docker build / dash で確認）`）
    - 検証節を作るのは、検証そのものが変更の主眼のときだけ。それ以外はテスト結果を `## 変更内容` の末尾に 1〜2 行で足す
    - 詳細な根拠・再現手順・引用が必要なら PR 本文ではなくレビューコメントに書く。本文は「読んで判断できる最小」に保つ
    - 未検証・スコープ外は削らずに 1 行で明示する（省略ではなく圧縮する）

## 使用技術

- **Git コマンド**: ローカルリポジトリの操作、コミット、プッシュ
- **GitHub CLI (`gh`)**: PR作成、レビュワー設定、GitHub操作全般

## エラーハンドリング

- 未コミットの変更がない場合の警告
- リモートブランチが存在しない場合の処理
- PR作成時のエラー処理
- ネットワークエラーや認証エラーの処理

## 注意事項

- 実行前に現在のブランチが意図したものであることを確認
- 重要な変更の場合は、事前にバックアップを取ることを推奨
- PRタイトルと詳細は実行後に手動で調整可能
