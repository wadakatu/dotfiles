# issue に着手する前に重複を探す

「issue #N を対応して」で作業を始めたら、コードを読み始める前に同じ主旨の issue を探す。

- `gh issue list --search "<固有名> in:title,body" --state all` で探す。検索語は対象のシンボル・クラス名・API パスなどの固有名にする（`bug` `fix` のような一般語は役に立たない）
- タイトルに検索語を含まない issue もある。関連する tracking issue の子 issue と、コメントで挙がっている番号も開いて確かめる（起票時の重複検索も同じ）
- 古い issue はコードの現状とずれている一方、後から立った issue の方が実装仕様として完成していることがある。使える仕様があれば、それを設計の出発点にする
- 重複が見つかったら PR 本文に `Closes #A` `Closes #B` を並べる。どれを close するかは自分で決めず、根拠を添えてユーザーに確かめる
- CLOSED でも未解決のことがある。stale bot の自動クローズも `stateReason` が `NOT_PLANNED` になるので、「却下済み」と書く前にコメント欄が bot だけでないかを見る

**Why:** 起票時の重複チェックは defer-to-issue skill が担うが、着手時の重複チェックは誰も担っていない。設計・実装・レビューを一通り終えた最後に、同じ箇所・同じ方針の仕様がそのまま使える形で後発の issue に書かれていたと分かったことがある。先に検索していれば、現在地を調べ直す手間を省けた。起票時にもキーワード検索だけで「該当なし」とし、タイトルに検索語を含まない既存 issue を見落としたことがある。
