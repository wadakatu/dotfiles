# サブエージェントの調査結果を外に出す前に

- サブエージェントや設計エージェントの調査結果を issue / PR / レポートなど外に出る成果物に載せる前に、載せる**全件**について
  `file:line` を開き、引用が実在することを自分で確かめる。上位の指摘だけ見て済ませない
- vendor やフレームワークの内部挙動についての主張は、vendor のソースを読んで確かめる。推測で書かれていることがある
- 確かめられなかったものは「未検証」として分け、断定した書き方で公開物に載せない。誤りが見つかったら、元のレポートにも訂正を残す
- 設計書の検証手順に書かれた「期待値」の例示を、実測値として成果物に書き写さない。数値を書くときは、自分のツール出力のどの行から取ったかを言えること

**Why:** 調査結果を起票する前にユーザーから「起票前にちゃんと全て検証をしましょう」と指示され、実際にそれで誤りが止まった。
サブエージェントは「reCAPTCHA の検証にタイムアウトが無い」と報告したが、ライブラリのソースを読むと、curl が使えるときは
60 秒のタイムアウトを明示的に設定する実装が選ばれていた。「無限」と「60 秒で有界」では issue の優先度がまるで違う。
ほかにも、存在しないファイルパスや既存コードの意図の取り違えがあった。設計書の検証計画にあった例示の値を docs に「Measured」として書き、
実際に測った値と食い違ったこともある。docs が実測の記録であるリポジトリでは、捏造したデータ点になる。
