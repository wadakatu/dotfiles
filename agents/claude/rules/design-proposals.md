# 設計案の出し方

設計案の承認を AskUserQuestion で求める前に、公式ドキュメントとフレームワークの実装まで当たって
「標準のやり方は何か」「自分の案はそこからどう外れるか」を先に示す。コードを読んで筋の通った案を作るところまででは足りない。

出すべき形:

- 使う API が公式ドキュメントどおりか（URL 付き）
- フレームワーク自身が同じ問題をどう扱っているか（vendor の実装を読む）
- **自分の案が標準から外れている点と、それでも外す理由**（リポジトリ側の根拠 = rules / 既存の前例）
- 運用・セキュリティ方針の選択肢は、規格（NIST など）に加えて、主要サービス（GitHub・Okta・Microsoft など）が実際にどうしているかを
  一次資料で集め、それに照らしてから聞く

**Why:** 承認を求めた設計案が差し戻され、「この設計はベストプラクティスに沿っていますか？」と聞かれることが繰り返しあった。
例: 例外のログレベルを下げる案を出したが、フレームワーク自身はクライアント起因の例外を「そもそも report しない」立場で、
公式のマーカーインターフェースもあった。それを先に示さずに承認を求めたのが差し戻しの原因で、最終設計はそこから決まった。
規格の節番号は引いていたが、他社の実例を調べずに自分で組んだ案を並べて差し戻された回もある。
「動く案」と「その領域で正しいとされている案」は別物で、ユーザーが見ているのは後者。裏取りを承認後に回すと設計をやり直すことになる。
