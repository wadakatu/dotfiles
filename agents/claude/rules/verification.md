# 検証

## 退化した本番状態で選択ロジックを検証したことにしない

- 配列から 1 つ選ぶ・条件で絞る・順序に依存するコード（`jq` 式や CLI の `--format` を含む）は、本番で実行して正しい値が返っても
  **フィールドパスの検証**にしかならず、**選択ロジックの検証**にはならない。本番が退化ケース（要素 1 つ、100%、単一候補）なら、
  どんな選び方でも同じ答えになる
- 本番実測に加えて**合成入力**を通す。候補が 2 つ以上・境界値・キー欠落を必ず含める。1 行で足りる:

  ```bash
  echo '{"status":{"traffic":[{"revisionName":"svc-new","tag":"canary","percent":0},
    {"revisionName":"svc-old","percent":100},{"revisionName":"svc-x"}]}}' | jq -r '<式>'
  ```

- ドキュメントに書くコマンドは、自分のテスト版ではなく**書いた形のまま**切り出して実行する

**Why:** Cloud Run の `status.traffic[0].revisionName` を「配信中の revision」として runbook に書き、本番で実行して正しい revision が
返るのを確認した。だが本番の `status.traffic` は 1 要素だけで、「先頭 = 配信中」が成り立つかは何も試せていなかった。実際には canary
（`--no-traffic --tag=canary`）が percent 0 の entry として配列に入り、順序の契約も無い。段階的なロールアウト中は配信中の revision が
複数ある。退化ケースは「通った」という強い信号を返すのに情報量がゼロで、しかも本番は平常時ほど退化しているので、いちばん試したいときに
いちばん役に立たない。
