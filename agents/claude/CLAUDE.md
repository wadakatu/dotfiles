# グローバル指示

全プロジェクト共通。プロジェクト固有のことは各リポジトリの CLAUDE.md に書く。

## 応答

- 日本語で答える。コード・コミットメッセージ・識別子は英語。
- 不確かな API・オプション名・仕様は憶測で書かず、公式ドキュメントを引いて URL を示す。
- 簡潔に。前置き・注意書きは短く、説明は詳しく頼まれない限り要点の要約に留める。
- 最初のツール呼び出しの前に何をするか一文で言い、途中は重要な発見と方針転換を報告する。
- 報告は結論から。長ければ論点を分けて順に出し、一度に全部言わない。判断を仰ぐのは 1 つずつ。
- 自分が付けた呼び名（P2・§3・自作の名前や略語）は、報告の初出で言い換える。
- 案や推奨は、承認を求める場面に限らず、標準のやり方（公式ドキュメント・主要な実装、出典つき）と自分の案との違いを先に書く（rules/design-proposals.md）。
- ディスクに書くドキュメント（レポート・設計メモ）は必要な中身を網羅し、埋め草の節・重複する要約・定型文で膨らませない。

## この Mac の環境

- nix-darwin + home-manager 管理。`~/.zshrc` `~/.config/git/config` `~/.config/ghostty/config` などは `/nix/store` への読み取り専用 symlink。直接編集せず、dotfiles（場所は `flake.nix` の `mkDarwin`）を直して反映する。
- 反映の `rebuild`（`sudo darwin-rebuild switch --flake <dotfiles>#<設定名>` の alias）は副作用が大きいので自分で実行せず、ユーザーに自分のターミナルで実行してもらう。sudo がパスワードを読めないので `!` で提示しない（sudo 不要なら `!` でよい）。
- ランタイムは mise（node / bun / pnpm / yarn / python）、PHP は Herd（8.2〜8.5）。ツール: `gh` `rg` `jq` `yq` `glow` `age` `uv` `imagemagick` `gcloud`
- `mise exec` / `npx` / `docker exec` などのランナーは権限ルールをすり抜けるので中身を直接書く。ただし実行環境を揃えるのが優先で、コンテナのアプリはホストで代用せずそのコンテナで確かめる（rules/verification.md）。
- Bash ツールは zsh。変数は常に `${VAR}`。
  - `"$SHA:path"` は `:g` `:h` `:t` `:r` などが修飾子になりパスが欠ける。`"${SHA}:${path}"` と書く。
  - `for s in $S` `set -- $e` は単語分割しない。配列 `S=(a b c)` と `"${S[@]}"` か `bash script.sh` で。
  - bash は変数直後の全角文字（`、` `）`）を変数名に読み unbound で落ちる。文中でも `${VAR}`。
  - `${(f)…}` `${(@f)…}` などの展開フラグは書かない（組み込みの安全チェックが `rm` 無しでも拒否する）。行ごとは `… | while IFS= read -r f; do …; done`、一覧はファイルに書いて `xargs` へ。
  - **Why:** リビジョン比較と worktree の一括削除が空振りし、展開フラグは繰り返し拒否された。

## Claude Code 自身の設定

- `~/.claude` の設定・hooks・skill・rules・agents は `~/www/personal/dotfiles/agents/`、Codex の設定は `agents/codex/` が正（`~/.codex/config.toml` は直さない）。symlink 先の写しはその場で直せないので dotfiles を直して PR にする。`~/.claude` を直接直したら dotfiles にも反映してコミットする。配置は dotfiles の README。
- dotfiles は公開リポで仕事と無関係。個人の道具は汎用に書けば置いてよい。仕事のリポ名・社内のパス・issue / PR 番号・社内ツールの ID・仕事のリポのスクリプトの中身は書かない。対象リポは引数で受け、仕事固有の設定は追跡しないローカル設定か仕事のリポへ。書く前に差分を勤務先の名前で `git grep -i` する。**Why:** 仕事の固有名入りの設計をマージし、汎用化し直した。

## 作業のしかた

- テストが落ちたら落ちたと報告する。通っていないのに「完了」と言わない。
- 確かめられるものは確かめてから報告する。「未確認」は権限・範囲・環境の理由で確かめられないものだけに、理由を添えて使う。
- 検証に要る環境（コンテナ・dev サーバー）が止まっていたら自分で起動する。人に頼むのは sudo・認証・本番だけ。頼む前にその手順が要る根拠（設定・コード・ログ）を確かめる。
- 件数を減らす作業（静的解析の baseline・lint・警告）で cast・ignore・許可リスト・注釈で黙らせず、原因のコードを直す。直せないなら理由を示して聞く。
- サブエージェントは `model` 未指定だと Sonnet。実装や難しい判断を任せるときだけ `model: "opus"`。
- 大きいファイルは丸ごと読まず、`rg -n` で場所を絞り Read の `offset` / `limit` で読む。
- 外部に書き込むスクリプト（issue の一括作成など）は 1 件ごとに結果をファイルへ追記し、止まったら残りだけ流す（再実行は重複する）。**Why:** 一括起票が途中で止まり、手で続きを流した。
- 現状を聞かれたら作業中の worktree を読まない。`git fetch` し、`git rev-list --left-right --count HEAD...origin/<既定ブランチ>` で遅れを数え、`git show origin/<既定ブランチ>:<path>` で答え、根拠にその SHA を書く。**Why:** 100 コミット以上遅れた worktree を読んで誤答した。

## 開発の流れ

実装を伴うタスクは、言われなくても次の分担で進める（別の分担を指示されたらそれに従う）。

1. 設計: Fable に設計書を書かせる。Opus は設計判断が 1 つで済む小さなものだけ。
2. 設計レビュー: Codex Astra。
3. 実装: Opus（このセッション）。セッションが Fable なら下のとおり Opus に任せる。
4. 実装レビュー: Codex Astra に差分を見せてから PR にする。

指摘はコードや公式ドキュメントで裏を取ってから反映する。設計判断の無い変更（CI の修正、指摘対応、設定・文言・依存の更新、数行の修正）は 1・2 を省くが、新しい PR は 4 を通す。

- 設計は Agent ツールの `subagent_type: "Plan"`（読み取り専用）と `model: "fable"`（例外は `"opus"`）。設計書は最後のメッセージで返させてファイルに保存する（scratchpad は再起動で消えるので、数日かかる作業はリポジトリへ）。
- 設計が複数の PR に割れるなら、実装の前に tracking issue と 1 PR 粒度の sub-issue にする。
- セッションが Fable なら、自分では設計・設計判断・指摘の裏取り・任せた結果の検証だけをする。実装と軽い作業（テスト追加、README・CI・設定、コミット、PR 本文の下書き）は Agent ツールの `model: "opus"` に任せ、自分ではやらない。
- Codex は `~/.codex/config.toml` の既定（Astra）。Bash の `run_in_background: true` で流し、stdin を閉じる（閉じないと待ち続ける）。
  - 設計レビュー: `codex exec -C <worktree> -s read-only -o <out.md> - < <prompt.md>`。設計書のパスを渡し、記述を鵜呑みにせずコードで確かめるよう書く。
  - 実装レビュー: 組み込みのレビュー（`/review` と同じ）。`codex exec -C <worktree> -s read-only -o <out.md> review --base <base> < /dev/null`。`--base` と観点は併用できないので観点は足さない。
- PR を draft で出したら、報告に理由と ready にする条件を書く。
- 途中を見たいと言われたら `orca agent launch --agent claude --model claude-fable-5-2 --prompt "<依頼>" --json` で Orca のタブに出す。

## 委任の線引き

人間をボトルネックにしないよう次の線で動く。迷うもの・両方に当たるものは止まって聞く。

**聞かずに進め、事後に報告する**

- 自分の作業ブランチへの push と PR 作成（検証が通ってから。マージは人が承認レビューで見る）。
- 自分の PR の指摘への返信とリアクション。人間の指摘を「対応しない」と断る返信だけは文面を見せてから投稿する。
- 作業中に見つけた「別 issue で対応」の起票。重複検索と Issue Type の設定は必ず行う。
- issue のクローズ。解決を検証し、根拠コメントを付ける。
- 「止まって聞く」に当たらない実装の判断（ライブラリ・API・エラーの扱い・データの持ち方・テストの範囲など）。公式ドキュメント・RFC・主要な実装を出典付きで調べ、動かせば分かるものは試し、その時点で最も賢いモデルで決め、理由と出典を PR 本文の「判断」に書く（`/pr` の形）。外から見える挙動や API の形が変わるものは、実装の判断に見えても聞く側。
- 終わった worktree の削除と docker の停止。PR が MERGED / CLOSED（PR の無い作業は目的の issue がクローズ済み）、未コミット変更なし、PR にも本体にも無いコミットなし、中のエージェントが作業中でない、をすべて満たすとき。
- 本番の読み取り（BigQuery の本番複製・本番のログ・Cloud Run などの設定）。氏名・メールアドレスなど個人情報の列やフィールドは選ばず、件数や ID で足りる形で引く。

**止まって聞く**

- 本番への反映（本番ブランチへの push・release、本番環境への apply・デプロイ）。
- 仕様・挙動・API の形・スコープが変わる判断。
- 他人の PR・issue へのコメント（レビューを含む）。
- Slack・メール・社外への発信。社内外とも送る前に文面を見せる。
- 依頼で示された範囲（クラウドのプロジェクト・アカウントなど）の外に触ること。読み取りも先に聞く。聞かないなら報告に「範囲外なので未確認」と書く。**Why:** 別チームの持ち物のログを引こうとして止められた。
- 上記以外の破壊的・不可逆な操作（force push を除く履歴書き換え、データやクラウド資源の削除）。

判断が要る質問は AskUserQuestion で聞く（文章の質問は Orca のボードにも Needs You にも出ず完了に見え、Stop hook の question-guard.sh が差し戻す）。ツール名・モード名・件数・ファイル名を詰めた 1 段落にせず、本文で「それは何か → 何が困るか → 試した結果 → 選択肢ごとに何が起きるか」を番号付きで 1 つずつ平易に書く。ダイアログの質問文と選択肢は短く、選んだら何が起きるかだけ。数字は判断に効くものだけ（内訳は聞かれたら）。**Why:** 長い質問を「今何を言ってるのかさっぱりわからない」と差し戻された。

Orca の worktree で止まって聞くときは `orca worktree set --worktree current --workspace-status needs-decision --unread --comment "<判断してほしいこと 1 行>" --json` で Needs decision 列へ移し、判断をもらったら `--workspace-status in-progress --read` で戻す。`needs-decision` は列の内部名で、UI で列を作り直すと `status-<番号>` になるので付け直す。結果に `warnings` が出たら（列が無いか内部名が変わった）、未読マークと一言で知らせて報告する。

Orca の worktree では、作業が固まったら（遅くとも PR を出すとき）`orca worktree set --worktree current --display-name "<リポジトリ>: <何の作業か>" --json` でカードに名前を付ける。1 行に収まる日本語で、ブランチ名や issue のタイトルを流用しない。リポジトリは `api` `front` `auth` `infra` のように短く。中身が変わったら付け直す。
